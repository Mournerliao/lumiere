## Epic Review

Epic 1 set out to prove Lumiere's core HDR preview promise: a Windows Graphics Capture FP16 frame can reach a Direct3D/DXGI scRGB swap-chain preview without SDR bitmap fallback, and the app can visibly report whether the preview is HDR-ready.

All Epic 1 stories are complete:

- Story 1.1: Scaffold the native Windows app foundation - done
- Story 1.2: Centralize HDR constants and preview readiness status - done
- Story 1.3: Create D3D11 device and WinRT/DXGI interop bridge - done
- Story 1.4: Attach an FP16 scRGB swap chain to SwapChainPanel - done
- Story 1.5: Prove minimal WGC FP16 capture to live preview - done

## Validation Outcome

Windows manual validation is now recorded as passed for the Epic 1 core path.

Observed result:

- The app launched successfully on Windows.
- The user selected a capture target.
- The app reached `HDR-ready`.
- Runtime diagnostics reported that `Direct3D11CaptureFrame.Surface` reached the FP16 scRGB swap chain without CPU readback.
- The preview presented live frames, proving the WGC -> D3D11 texture -> FP16/scRGB swap-chain path on real Windows hardware.

Validation level:

- Windows local restore/build/test/format had already passed during story execution.
- Windows manual validation now passed for the minimal HDR preview proof path.
- Full Epic 2 lifecycle behavior remains out of scope and not started.

## What Went Well

- The architecture boundaries held up under real Windows interop pressure: capture, graphics, infrastructure, and app wiring stayed separated.
- The readiness vocabulary was useful during debugging. `Initializing preview`, `Preview failed`, and `HDR-ready` made it clear which stage was active.
- Detailed diagnostics turned opaque COM/WinRT failures into actionable stack traces and native interop fixes.
- The project avoided SDR bitmap fallback, `SoftwareBitmap`, `BitmapImage`, GDI, and CPU readback in the routine preview path.

## Challenges

- Several Windows interop APIs behaved differently than the initial library-level assumptions suggested.
- Vortice and .NET COM marshalling helpers were not always safe for the exact WinRT/DXGI path required here.
- Some generated planning/story text contains encoding corruption, which makes retro and story review noisier than it should be.
- The successful preview still exposes follow-up UI/HDR presentation polish needs, including fit-to-window behavior and tone/display interpretation work.

## Key Learnings

- For critical WinRT/DXGI interop, explicit ABI-level handling can be more reliable than convenience wrappers.
- Manual Windows hardware validation should be treated as a separate validation level from Windows build/test success.
- The most useful diagnostic surface is stage-specific and close to the failure boundary.
- Epic 1 correctly proved the foundation, but it should not be allowed to blur into Epic 2 lifecycle claims.
