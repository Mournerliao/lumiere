# Epic 5 Retrospective: Native v0 Main Window and Settings Experience

Date: 2026-05-23
Epic status: done
Retrospective status: complete

## Epic Review

Epic 5 delivered the native v0 main window and settings experience for Lumiere. The epic completed six stories:

1. `5-1-build-the-native-v0-main-panel`
2. `5-2-implement-settings-navigation-and-shell`
3. `5-3-add-shortcut-and-hdr-alert-settings-ui`
4. `5-4-add-output-preference-settings-ui`
5. `5-5-persist-local-settings-across-launches`
6. `5-6-show-native-about-and-version-information`

All six stories are marked `done` in sprint tracking. The epic now provides a compact native WinUI shell with main capture actions, settings navigation, shortcut and HDR alert settings surface, honest pending output preferences, durable local settings storage, and About/version information sourced from build metadata.

## What Went Well

- The Epic 4 guardrail that `MainWindow.xaml.cs` must not become the application layer was applied consistently. UI work stayed mostly in native projection and composition paths, while settings ownership moved into `Lumiere.Settings`.
- Story 5.4 exposed and fixed a major validation problem: App-facing pure projections were moved into `Lumiere.App.Core`, which resolved the WinUI app-referencing testhost hang and made the graphics test suite reliable again.
- The settings surface stayed honest about future behavior. Shortcut editing remained pending Epic 7, output controls remained pending Epic 6, and copy avoided HDR-preserving output claims.
- Story 5.5 converted settings from an in-session stub into a schema-versioned local JSON source with safe defaults, fallback diagnostics, and focused tests.
- Story 5.6 removed fragile About copy/version literals from the actual projected UI path and made the displayed app identity come from assembly/build metadata.

## Challenges

- Several stories uncovered validation friction before the projection extraction. The testhost hang made early story completion harder to prove until App projection logic was separated from the WinUI executable.
- NuGet restore remains environment-sensitive under sandboxed execution. The validation evidence is good, but the workflow repeatedly needed explicit network permission for `dotnet restore`.
- CRLF formatting drift appeared after manual patches. `dotnet format` caught it reliably, but it added avoidable validation churn.
- Rendered WinUI validation still lags behind projection-level confidence. Automated tests prove the projection logic, but actual settings visuals, text scaling, high contrast, screen reader output, and packaged version display still need Windows manual validation evidence.

## Previous Retro Follow-Through

Epic 4 recommended three key guardrails for Epic 5:

- Create durable Epic 5 implementation guidance so `MainWindow` does not absorb settings/output/tray/hotkey logic.
- Keep unsupported controls scoped honestly.
- Introduce a settings write/persistence plan before editable settings become real behavior.

Follow-through was strong:

- `_bmad-output/implementation-artifacts/epic-5-implementation-guardrails.md` was used as active story context.
- Stories 5.3 and 5.4 kept unsupported hotkey/output controls read-only or explicitly pending.
- Story 5.5 implemented local settings persistence in `Lumiere.Settings` instead of UI-local state.

The remaining carry-forward item is manual UX/accessibility validation for the rendered settings shell.

## Technical Lessons

- Pure projection code should not live in or require the WinUI executable when it can be tested in a lightweight project. `Lumiere.App.Core` is now the right home for app-facing projection logic.
- Settings need separate read and write seams. `ISettingsProvider` remains the shared read source, while specific writer seams can be added deliberately when settings become editable.
- Pending UI is still product behavior. Disabled/read-only controls need accessible help text, non-color state cues, and copy that clearly states what is not implemented yet.
- Version/About metadata should be projected like other settings shell data; XAML literals are acceptable only as design-time placeholders, not as the authoritative runtime source.

## Critical Path Before Starting Epic 6 Stories

- Preserve the Epic 5 boundary rule: `MainWindow.xaml.cs` may route and project, but output target policy, file writes, naming, per-target feedback, and after-capture behavior must live behind owning-module abstractions.
- Treat `ISettingsProvider` as the shared settings source for output behavior. Avoid creating a separate output-local preference cache.
- Keep all folder picker, shell reveal/open, file permission, and path validation interop behind the appropriate platform boundary.
- Decide how Epic 6 validation will separate automated output policy tests from Windows manual clipboard/file output validation.
