## Architecture Assessment

Verdict: the current implementation architecture is directionally sound and materially better than the pre-Epic 4 shape, but it is not yet elegant. It is a stable MVP foundation with one remaining concentration of complexity: `MainWindow.xaml.cs`.

### What Is Working

- Module ownership is mostly coherent. Capture state and WGC session lifecycle live in `Lumiere.Capture`; D3D11/DXGI/HDR and output conversion live in `Lumiere.Graphics`; WinRT/COM/Win32 interop stays in `Lumiere.Infrastructure`; overlay/crop behavior stays in `Lumiere.Overlay`; settings now has a real boundary.
- `CaptureService` owns the shared capture session state and uses `TryReserveCommand()` to atomically guard command entry. This is a strong foundation for future tray and hotkey entry points.
- `ICaptureCommandCoordinator`, `IOutputService`, and `ISettingsProvider` are appropriately narrow. They create a useful app-facing seam without introducing a DI framework or speculative service layer.
- The HDR preview invariant remains intact. No scan found `BitmapImage`, `SoftwareBitmap`, WIC/GDI preview fallback, or ordinary XAML image presentation replacing the FP16/scRGB path.
- Lifecycle diagnostics improved substantially. Stale callback rejection, teardown, preview detach, swap-chain release, and output failure paths now have structured logs.
- Overlay UX moved closer to the MVP model: visible cancel affordance, completion feedback, invalid crop feedback, and retry behavior are represented in typed overlay states and tests.

### Architecture Concerns

1. `MainWindow.xaml.cs` is still the orchestration pressure point.

   It consumes the new seams, but it still directly coordinates direct monitor target selection, preview/swap-chain lifecycle, overlay creation and events, output request construction, session state projection, UI-thread marshalling, and teardown. This is acceptable for the current MVP transition, but Epic 5-7 will likely make it unwieldy if new UI, settings, tray, and hotkey behavior are added directly there.

2. `Lumiere.App` still knows more concrete infrastructure than the architecture wants long-term.

   `App.xaml.cs` manually wires `GraphicsDeviceResources`, `CaptureService`, `CaptureCommandCoordinator`, `ClipboardOutputService`, and `DefaultSettingsProvider`. Manual composition is the right choice now, but ownership should stay explicit as more services arrive.

3. Cross-module shared data types are pragmatic but slightly awkward.

   `CropPixelRect` and `OutputTarget` are in `Lumiere.Graphics.Output`, which allows `Lumiere.Overlay` and `Lumiere.Settings` to consume common output-facing types. This is acceptable for now, but Epic 6 should deliberately confirm whether `Graphics.Output` is the long-term home for output policy vocabulary.

4. `ISettingsProvider` is injected but not yet behaviorally integrated.

   This was intentional in Story 4.4, but Epic 5 should be careful not to create UI-local settings state that later has to be reconciled with the provider.

5. Some deferred work is encoded but not yet operationally tracked.

   `deferred-work.md` contains several real items: duplicated command rejection logic, `ApplySessionState` reentrancy behavior, missing InvalidCrop integration tests, and validation gaps. These are not blockers, but they should be converted into story-scoped work when relevant.

## What Went Well

- The team corrected the largest architectural risk from Epic 3: capture commands now pass through a shared session guard instead of UI-local assumptions.
- Direct monitor capture is clearly the default path, and picker behavior has been demoted to fallback/debug vocabulary.
- The main window is no longer a dashboard prototype; it is closer to the compact capture-first MVP shell.
- The overlay UX deviations discovered in Epic 3 were not ignored. They became concrete code and tests in Story 4.6.
- Windows validation and structured logs now provide much better evidence for repeated lifecycle behavior.

## Challenges

- Story 4.5 became a hybrid validation/fix story. Some fixes were accepted as pragmatic, but the process boundary blurred.
- Review findings accumulated across stories, and several deferred items are still written as notes rather than executable follow-up work.
- `MainWindow.xaml.cs` remains the place where multiple subsystems meet. The new seams reduce risk, but the file still carries too much workflow knowledge.
- Validation coverage is still uneven: multi-monitor, SDR, DPI variants beyond the tested configuration, Escape scenarios from Story 4.5, and clipboard lock recovery remain gaps.
- Some story records contain mojibake in review sections, which makes future evidence extraction harder.

## Key Learnings

1. Seams work best when they are created just before the next pressure arrives.

   `ICaptureCommandCoordinator`, `IOutputService`, and `ISettingsProvider` were small enough to help without becoming architecture theater. Epic 5 should continue this style: extract the next real workflow boundary, not a generic framework.

2. `MainWindow` should now be treated as a composition and projection surface, not a place to grow new product logic.

   Future work should prefer small workflow coordinators for settings navigation, output policy, tray commands, and hotkeys.

3. Manual validation is most valuable when it produces follow-up stories, not only evidence tables.

   Story 4.5 found real gaps. The next step is to route those gaps into Epic 8 or targeted implementation stories instead of letting them remain prose-only.

4. HDR claim discipline is holding.

   The code and docs continue to distinguish FP16/scRGB preview from basic bitmap clipboard output. This is one of the healthiest architectural habits in the project.

5. Review needs to keep checking architecture intent against actual call sites.

   The interfaces are present, but the important question is whether future features use them instead of reaching back into `MainWindow` or native resources.

## Next Epic Preparation

Epic 5 is the native v0 main window and settings experience. Its plan is still broadly sound, but it should respect the architecture pressure exposed in Epic 4.

### Recommended Epic 5 Guardrails

- Treat `MainWindow.xaml.cs` size and responsibility as a risk. Do not add settings workflows, state persistence, output option semantics, tray projection, or hotkey registration directly into it.
- Build settings UI against `ISettingsProvider` and a planned write/persistence counterpart. Avoid UI-local duplicate settings state.
- Keep unsupported settings disabled, read-only, or clearly pending until Epic 6 and Epic 7 implement behavior.
- Preserve the direct capture command path through `ICaptureCommandCoordinator` for any main-window action.
- Keep output settings honest: UI may expose planned controls only when support status is explicit and non-misleading.
- Use rendered/manual review for UI density and state clarity, but do not confuse that with HDR/WGC/DXGI hardware validation.
