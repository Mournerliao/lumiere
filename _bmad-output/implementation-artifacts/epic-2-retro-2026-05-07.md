## Epic Review

Epic 2 set out to productize the capture lifecycle after Epic 1 proved the FP16/scRGB preview path. The epic moved Lumiere from a successful preview proof into a more trustworthy capture experience: target selection is typed, cancellation is recoverable, capture state is explicit, teardown and restart are deterministic, repeated lifecycle behavior has automated evidence plus a manual validation checklist, and the default MVP path enters direct monitor capture without a picker.

All Epic 2 stories are complete:

- Story 2.2: Represent capture session state explicitly - done

## What Went Well

- **State model maturity** — `CaptureSessionState` with `Idle`, `SelectingTarget`, `Initializing`, `Capturing`, `Degraded`, `Unsupported`, `Failed`, and `Disposed` became the single lifecycle contract. All 5 stories consumed it without creating parallel status systems.
- **HDR constraint preserved** — Every story explicitly banned `BitmapImage`, `SoftwareBitmap`, GDI, CPU readback, and SDR fallback in the main preview path. The product's core value was protected across the entire epic.
- **Hardware-independent test seams** — `CaptureTarget.CreateForTest`, injectable delegates for monitor resolution, fake picker interfaces, and resource-independent lifecycle validation gave solid CI coverage without real GPU hardware.
- **Lifecycle safety held** — `previewGeneration` guard, deterministic teardown ordering, detach-before-release, and generation-scoped callbacks survived 5 stories without regression.
- **Cancellation as normal path** — Picker cancellation and Escape cancel were treated as ordinary product flows, not failure-shaped edge cases.
- **Teardown ordering became observable** — Capture disposal evidence and swap-chain detach-before-release evidence are now represented in code and tests.

## Challenges

- **COM interop complexity** — Story 2.5 had 16 review findings, with COM pointer lifecycle issues dominating (`Marshal.FreeHGlobal` on COM pointers, leaked activation factories, fragile vtable indices, `FromAbi` ownership semantics).
- **MainWindow orchestration weight** — Every story added more lifecycle orchestration to `MainWindow.xaml.cs` — stop, restart, frame-size recreation, direct monitor wiring. The file is accumulating responsibility.
- **Validation gap** — Zero Windows manual-pass across all 5 stories. Story 2.5 (the default MVP capture path) is only Mac-pass. The lifecycle checklist exists but hasn't been run on real hardware.
- **Evidence disposal** — Production resource owners (`CaptureSessionResources`, `SwapChainResources`) return teardown evidence but discard it. Diagnostic infrastructure exists only in tests.
- **Encoding corruption** — Older generated story text contains mojibake, making retro and review noisier than necessary.

## Key Learnings

1. **Typed state snapshots beat scattered labels** — `CaptureSessionState` let product UI, tests, and future overlay code reason about the same lifecycle facts.
2. **COM pointer lifecycle needs explicit ownership patterns** — Ad-hoc cleanup in `finally` blocks is not sufficient for ABI-level interop. Infrastructure needs a consistent COM ownership model.
3. **Injectable delegates are the right hardware seam** — `Func<IntPtr>` for monitor resolver, `Func<IntPtr, GraphicsCaptureItem>` for item factory kept tests hardware-independent without over-abstracting.
4. **Manual validation checklists are part of the trust story** — The lifecycle checklist is not optional QA; it's evidence that the product behaves correctly on real hardware.
5. **Lifecycle safety depends on sequencing, not just disposal** — Clearing references, invalidating generations, detaching preview, and releasing native resources all need the right relationship.
