## Epic Review

Epic 3 set out to build the fullscreen overlay crop workflow on top of the proven HDR preview foundation from Epic 1 and the capture lifecycle from Epic 2. The goal was to let users interact with a fullscreen capture overlay, create and adjust a crop selection over the HDR preview, confirm the selected region, or cancel and return safely to the desktop.

## What Went Well

- Architecture boundaries held strong: `Lumiere.Overlay` clearly owned crop UI, `Lumiere.App` only did composition wiring, and capture/graphics ownership remained untouched.
- The HDR preview path was preserved throughout the crop workflow - no SDR bitmap, CPU readback, or GDI fallback was introduced.
- The crop domain model was well-designed: `CropController`, `CropGeometry`, `CropSelection`, and `CropCoordinateMapper` have clear responsibilities and no WinUI/WGC/D3D11 dependencies.
- Coordinate mapping was implemented as a pure function with deterministic rounding (floor for left/top, ceiling for right/bottom), preventing edge pixel loss.
- Hardware-independent test coverage grew healthily: overlay state, crop controller, coordinate mapping, confirm logic, and hit-test mode all have automated tests.
- All 5 action items from Epic 2 retrospective were executed in Epic 3.

## Challenges

- `MainWindow.xaml.cs` continues to carry significant orchestration weight. Stories 3.1 and 3.4 both required refactoring overlay-related logic out of this file, and it still owns target selection, capture startup, frame callbacks, overlay lifetime, and teardown.
- Resource disposal edge cases were primarily caught during code review rather than proactively prevented during development: UI dispatch swap-chain release, stale overlay teardown, pointer ownership.
- Degraded state visual distinction was not addressed early enough - Story 3.1 review found that `Degraded preview`, `Unsupported capture`, and `Preview failed` states were not visually distinct from `HDR-ready`.
- Real hardware validation was deferred to the end - all stories marked `Windows CI-pass` with `Windows manual-pass` pending until final verification.

## Key Learnings

- Domain model separation pays off: crop types that don't depend on WinUI or graphics APIs are easier to test and reason about.
- Pure functions for coordinate mapping eliminate an entire class of integration bugs.
- Reusing existing teardown paths (like `StopPreview()` and `CloseOverlayWindow()`) is safer than creating parallel cleanup paths.
- Hit-testing behavior should be explicit and tested early, not assumed as a side effect of window styles.
- The distinction between `CaptureConfirmed` and `CloseRequested` events prevented a class of semantic confusion bugs.

## Follow-Through From Epic 2 Retro

Epic 2 retrospective committed to 5 action items for Epic 3. All were executed:

- **Completed**: Story 3.2 treated preview bounds and coordinate mapping as first-class contracts through `CropCoordinateMapper` and `OverlayPreviewLayout.PreviewBounds`.
- **Completed**: Story 3.3 preserved stable crop geometry when capture target size, scaling, or overlay layout changes through bounds clamping and minimum-size rejection.
- **Completed**: Story 3.4 wired confirm/cancel through existing teardown semantics (`StopPreview()`, `CloseOverlayWindow()`) instead of creating a second cleanup path.
- **Completed**: Story 3.5 kept hit testing deliberate with explicit `OverlayHitTestMode` defaulting to interactive mode, not pass-through.
- **Completed**: Epic 3 overlay code consumed `CaptureSessionState` through `OverlayState` mapping instead of inventing another status model.
