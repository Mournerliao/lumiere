# Epic 9 Retrospective: Settings Panel Completion

## Epic Review

Epic 9 completed the remaining settings controls that were disabled or read-only in the MVP settings panel. All six stories were implemented in a single session, enabling HDR alerts toggle, timestamp naming, save path selection with folder picker, after-capture behavior, shortcut editing with key capture dialog, and export color format selection (sRGB only; HDR10/P3 remain pending validation).

Completed stories:

- 9.1 Enable HDR Alerts Toggle
- 9.2 Enable Timestamp Naming Toggle
- 9.3 Enable Save Path Selection
- 9.4 Enable After-Capture Behavior Toggle
- 9.5 Enable Shortcut Editing
- 9.6 Enable Export Color Format Options

## What Went Well

- **Consistent writer interface pattern:** All six stories followed the same pattern: create `I*SettingsWriter` interface → implement in `DefaultSettingsProvider` → change `IsReadOnly` in projection → wire up UI click handler → inject via constructor. This consistency made implementation predictable and fast.
- **Single session completion:** All 6 stories were created, implemented, and validated in one session. The established patterns from Epics 4-8 made this possible.
- **Backward-compatible schema migration:** `LocalSettingsStore` was updated to accept both schema version 1 and 2, ensuring existing settings files load correctly with `ExportColorFormat` defaulting to "sRGB".
- **No new test failures introduced:** All 356 passing tests continued to pass. The 2 pre-existing `DefaultSettingsProviderTests` failures remain unresolved.
- **FolderPicker integration:** The `FolderPicker` with `InitializeWithWindow.Initialize()` follows the existing `GraphicsCapturePickerInterop` pattern.

## Challenges

- **XamlCompiler fragility:** `dotnet format` removing "unused" `using` statements (`Microsoft.UI.Xaml.Shapes`, `Vortice.Direct3D11`) caused cascading `WMC9999` XamlCompiler internal errors. This is a recurring issue — the XamlCompiler generates partial classes that depend on these imports, but the C# analyzer doesn't see the dependency.
- **Line ending inconsistencies:** New files created via `Write` tool default to LF line endings, while the project expects CRLF. Each new file required a `dotnet format` pass to fix.
- **Constructor parameter growth:** `MainWindow` constructor now takes 13 parameters (up from 8). This is a code smell that should be addressed in a future refactoring story.

## Key Learnings

- **Never let `dotnet format` remove `using` statements in WinUI projects.** The XamlCompiler generates code that depends on `using Microsoft.UI.Xaml.Shapes` and other imports that appear unused to the C# analyzer. Always verify build after running `dotnet format`.
- **Schema versioning needs forward compatibility.** Bumping from schema 1 to 2 required updating the `Validate()` method to accept both versions. Future schema changes should use a range check rather than strict equality.
- **Writer interface injection scales linearly.** Each new settings writer adds 1 constructor parameter. A settings writer aggregator or service locator pattern could reduce constructor bloat.
