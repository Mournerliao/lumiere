Date: 2026-05-04
Project: lumiere

## Epic Review

Epic 2 set out to productize the capture lifecycle after Epic 1 proved the FP16/scRGB preview path. The epic moved Lumiere from a successful preview proof into a more trustworthy capture experience: target selection is typed, cancellation is recoverable, capture state is explicit, teardown and restart are deterministic, and repeated lifecycle behavior has automated evidence plus a manual validation checklist.

All Epic 2 stories are complete:

- Story 2.1: Start capture and select a display or window target - done
- Story 2.2: Represent capture session state explicitly - done
- Story 2.3: Stop, restart, and recreate capture resources - done
- Story 2.4: Validate repeated capture lifecycle stability - done

## What Went Well

- The state vocabulary matured from readiness labels into a real session contract. `Idle`, `SelectingTarget`, `Initializing`, `Capturing`, `Degraded`, `Unsupported`, `Failed`, and `Disposed` now make lifecycle claims clearer.
- Cancellation became a normal product path rather than a failure-shaped edge case.
- Generation-scoped callbacks remained the central stale-frame defense across target selection, frame arrival, readiness updates, diagnostics callbacks, and resize/recreate work.
- Teardown ordering became observable: capture disposal evidence and swap-chain detach-before-release evidence are now represented in code and tests.
- The epic preserved the core product constraint: no SDR bitmap, GDI, CPU readback, or 8-bit fallback was introduced into the main preview path.

## Challenges

- `MainWindow.xaml.cs` continues to carry significant orchestration weight. The work stayed bounded, but Epic 3 should avoid letting overlay behavior pile more native lifecycle semantics into the app shell.
- Several review findings centered on race boundaries: stale target revival, generation invalidation order, delayed UI dispatch, and evidence being discarded by production resource owners.
- Encoding corruption remains visible in older generated story review notes. It does not block implementation, but it makes retrospectives and audits noisier.
- The distinction between Windows CI-pass and Windows manual-pass needs to stay explicit. Epic 2 has good automated lifecycle evidence, but real GPU/resource stability still needs hardware validation.

## Key Learnings

- Typed state snapshots are more valuable than scattered labels because they let product UI, tests, and future overlay code reason about the same lifecycle facts.
- Lifecycle safety depends on sequencing, not just disposal calls. Clearing references, invalidating generations, detaching preview, and releasing native resources all need to happen in the right relationship.
- Hardware-independent validation seams are effective for repeated lifecycle logic, but they cannot prove GPU memory stability or real frame-pool behavior.
- The manual validation checklist is now part of the product's trust story, not an optional QA appendix.

## Next Epic Preparation

Epic 3 is already in progress. Story 3.1 has introduced the fullscreen overlay shell above the HDR preview and preserved the Epic 2 lifecycle safeguards. The remaining Epic 3 stories need to build crop interaction without destabilizing the capture lifecycle.

Epic 3 preparation focus:

- Story 3.2 should treat preview bounds and coordinate mapping as first-class contracts before drag selection logic grows.
- Story 3.3 should preserve stable crop geometry when capture target size, scaling, or overlay layout changes.
- Story 3.4 should wire confirm/cancel through existing teardown semantics instead of creating a second cleanup path.
- Story 3.5 should keep hit testing deliberate; whole-window click-through behavior must not break crop selection or Escape/cancel recovery.
