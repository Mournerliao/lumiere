# Epic 6 Retrospective: Configured Output Users Can Trust

## Epic Review

Epic 6 completed the configured output path for Lumiere's MVP capture loop. The epic moved output from implicit clipboard-only behavior into a settings-backed policy that can route to clipboard, folder, or both; report per-target success, failure, and skipped outcomes; write timestamped PNG artifacts without overwriting; avoid unsupported HDR-preservation claims; and run supported after-capture actions only for file artifacts.

Completed stories:

- 6.1 Define Output Target Policy and Result Model
- 6.2 Implement Configured Clipboard Output
- 6.3 Implement Folder Output with Save Path and Timestamp Naming
- 6.4 Implement Both-Target Output and Completion Feedback
- 6.5 Scope Export and Color Format Options Honestly
- 6.6 Implement Supported After-Capture Behavior

## What Went Well

- The output policy/result model created in Story 6.1 stayed useful through every later story.
- Folder output reused the existing PNG encoder path instead of creating a second output conversion model.
- Per-target result records made both-target partial success and after-capture failure separation straightforward.
- Settings projection stayed honest: active behavior is shown as active, while unsupported editing, folder picking, and advanced color/export semantics remain read-only or unavailable.
- Validation discipline held: current output is described as basic PNG/clipboard/file usability, not validated HDR-preserving output.

## Challenges

- Restore and format verification require network/SDK behavior that can be blocked by the Codex sandbox; the workflow needs explicit escalation when NuGet access is required.
- `dotnet format --verify-no-changes` repeatedly exposed line-ending drift after patch edits; running `dotnet format --no-restore` before final verification is the reliable cleanup step.
- Windows shell open/reveal behavior can be routed and tested with fakes, but real Explorer/open behavior still needs Windows manual validation before release claims.

## Key Learnings

- Keep output results as typed aggregates. It prevented clipboard/folder/after-capture state from collapsing into ambiguous success strings.
- Treat after-capture as a post-output result, not another output target. That cleanly preserves output success when shell launch fails.
- Keep native launching in `Lumiere.Infrastructure.Interop` and compose it from `Lumiere.App`; this follows the platform boundary without pushing Windows shell details into UI code.
- Story-scoped tests are strongest when they assert routing and failure boundaries rather than UI copy alone.
